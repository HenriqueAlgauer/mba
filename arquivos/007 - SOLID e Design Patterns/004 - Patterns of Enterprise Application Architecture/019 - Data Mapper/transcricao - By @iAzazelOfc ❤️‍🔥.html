Bom, pessoal, da mesma forma que a gente pode trabalhar com Active Record, a gente tem outras opções para conseguir trabalhar. Uma dessas outras opções é chamada de Data Mapper. Agora um ponto que eu quero que você entenda claramente é, quando a gente está falando de Data Mapper, a gente está falando ainda de lógica que vai estar fazendo parte do seu domínio. Quando a gente fala em Data Table Gateway, em Row Table Gateway, a gente está falando de Gateway, de caras da porta para fora. A gente está falando em Data Mapper dos caras para dentro. Ou seja, qual é a ideia? Eu tenho o meu domínio complexo mapeado e no meio do caminho, antes do banco de dados, eu crio uma interface, uma abstração, que vai fazer com que eu fale com o banco de dados. Então, se você olhar, olha só que interessante, o Data Mapper é uma camada de mapeamento que move os dados entre os objetos de bancos de dados enquanto os mantém independente um do outro. O que significa, galera? Aqui em Person, se você olhar, nós temos o nosso domínio complexo. Eu posso ter diversas classes, diversos relacionamentos e tudo acontecendo. Aqui eu tenho a minha lógica de negócio. Aqui no banco de dados eu tenho as minhas tabelas de banco de dados. E para o meu domínio complexo falar com o meu banco de dados, eu coloco um cara no meio que eu chamo de Data Mapper. E esse Data Mapper, toda vez que eu vou inserir alguma coisa, alterar, fazer consultas acessa o banco, converte esses dados no padrão que eu preciso e depois faz uma hidratação desses dados nas minhas entidades dos meus domínios, que são ricos para eu conseguir trabalhar.

Então vamos lá. Vamos entender um pouco mais a fundo. Olha só, quando você deve utilizar Data Mapper? Domínio complexo. Por quê? Porque, nesse caso, o domínio complexo cresce 100% independente do seu banco de dados. E o cara que vai fazer com que o seu domínio complexo fale com o banco é exatamente essa abstração do Data Mapper. Então,isso é um ponto importantíssimo para você se ligar. Outro ponto importante, o seu Data Mapper, pelo fato dele ser uma camada entre o seu modelo de domínio e o seu banco de dados, ele é acoplado ao banco e é acoplado ao seu domínio. Isso significa que se eu mudar a modelagem do meu domínio, eu não necessariamente tenho que mudar o banco, mas se eu mudar o banco, eu não necessariamente tenho que mudar o meu domínio, porque quem cuida desse meu meio de campo é o Data Mapper. Eu não sei se você está conseguindo perceber a diferença entre o Data Mapper e o banco de dados e o Active Record. Porque o Active Record, a sua entidade de lógica de domínio, está colada diretamente no banco. Sua entidade estende o Active Record. Então, ela tem a responsabilidade de acessar o banco, mas ela também pode ter responsabilidade de domínio. Com o Data Mapper isso não ocorre, porque o seu domínio é uma coisa, o seu Data Mapper apenas faz intermediação e o seu banco de dados é outra coisa. Um ponto importante que eu sempre vou deixar claro também. O que muita gente faz, principalmente quando está trabalhando com Hibernate, com por exemplo diversos ORMs que adotam esse padrão, Doctrine para PHP e etc. O que normalmente esses ORMs costumam fazer? O ORM por padrão faz mapeamento de entidades com banco de dados, que no final do dia é o Data Mapper. Mas o que acontece? Lembra que eu falei para você que a baita desvantagem do Active Record é exatamente a tela lógica de domínio dentro da sua classe do Active Record? Pois é, muita gente cria a entidade, por exemplo, pessoa e faz o mapeamento através de annotations, não interessa a forma como ele faz, do Data Mapper para falar com o banco de dados. E a lógica de domínio está nessa entidade. Então, o que isso significa, galera? Significa que se for para você trabalhar desse jeito, é melhor você utilizar Active Record. Porque o Data Mapper separa o seu modelo de domínio da abstração do seu banco de dados. Então, muita gente quer aproveitar essa entidade de Mapper para utilizar essa entidade como domínio. Então o que ele faz? Ele tem uma entidade "pessoa" que tem nome, sobrenome, RG, CPF. Ele faz o mapeamento dessas colunas com o banco de dados e utiliza essa entidade para trabalhar com o seu modelo de domínio. Isso é o pior dos mundos, porque você tem a complexidade do Data Mapper e não tem os recursos do Active Record. Então, sempre a minha dica, quando você for utilizar Data Mapper,  é criar a modelagem de domínio. E crie a sua entidade do Data Mapper. Se você tem, por exemplo, uma classe "pessoa", você vai ter uma classe "pessoa", entidade de domínio e você vai ter uma outra classe "pessoa" para mapeamento do Data Mapper.

E o mapeamento do Data Mapper, o que ele vai fazer? Ele pode receber dados de domínio, fazer essa conversão e jogar para o banco de dados. Mas nunca misture a sua entidade de domínio com a sua entidade do Data Mapper. Isso que eu quero trazer para você. Então, outro ponto importante, você vai perceber que muita gente que faz essa mistura de entidade de domínio, de entidade com mapper e coloca tudo numa coisa só, para evitar que a lógica do domínio vaze para o banco de dados, acaba fazendo o quê? Não colocando lógica nenhuma dentro da entidade. E isso significa o quê? Que você começa a ter entidades anêmicas. E o que isso significa? Significa que você vai ter uma entidade somente com getSet e que não resolve o problema de domínio. E o que você faz? Você cria os tais dos services que tem toda a lógica de domínio.  No final do dia, você vai ter entidades anêmicas que no final do dia só estão falando com o banco de dados. Nesse caso, é melhor você utilizar o quê? ActiveRecord, já que você está trabalhando dessa forma.

Toma cuidado. Escolha o formato que você quer trabalhar. Se você for trabalhar com domínio anêmico, ok, muitas vezes não tem problema, principalmente quando você está trabalhando de um para um em sistemas mais simples. Agora domínio complexo, meu querido amigo ou amiga, esqueça trabalhar com domínio anêmico. Vai dar muito trabalho ao longo do tempo para você dar manutenção. Está errado porque é com domínio complexo, então você está usando Active Record e você está errado. Não, não é assim! Mas em via de regra, eu faria essa recomendação para você.
