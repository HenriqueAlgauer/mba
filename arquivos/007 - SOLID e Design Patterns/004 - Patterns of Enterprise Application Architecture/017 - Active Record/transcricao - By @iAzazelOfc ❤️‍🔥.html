Bom, pessoal, vamos falar um pouco sobre Active Record. Esse cara é absolutamente fantástico. O que ele faz? Ele fala que você tem um objeto que encapsula linha, tabela ou uma view e ainda tem a opção de adicionar lógica de domínio nos seus dados. Assim, toda vez que você está trabalhando com Active Record, você sente uma facilidade muito grande de você trabalhar, porque você fala, “pessoa traça o nome é igual ‘Wesley’, pessoa ponto save salvou”. Inserte pessoa “Wesley”, salvou no banco de dados. Get pessoa, vai isso, vai aquilo. Então, você consegue criar normalmente ainda métodos específicos e ele vai trazer os registros para você quando você trabalha com Active Record.

Active Record é extremamente simples de ser utilizado, porém, e é nesse ponto que a gente vai adicionando os “poréns”, você tem um acoplamento muito grande. Você vai perceber que as suas entidades do Active Record normalmente vão herdar uma classe base de Active Record que possui toda a lógica para você falar com o banco de dados. Então, você começa a ter um acoplamento extremamente forte com a forma de trabalhar com o banco de dados. Você tem que ter muito cuidado com isso. Eu não acho que isso necessariamente é errado, mas eu acredito que é uma ciência que você tem que ter na hora de escolher os tipos de persistência. E a gente vai falar, inclusive, um pouco mais sobre o Active Record de coisas que valem a pena você prestar atenção.

Então é o seguinte, o ActiveRecord vai carregar de um lado dados do banco, mas ele também consegue ter lógicas de comportamento. Isso é um ponto importante. Por quê? Porque você consegue adicionar lógica de domínio no Active Record e ainda adicionar toda a abertura que você tem com o banco de dados no mesmo cara. Isso se você começar a pensar em SOLID, talvez você quebre tranquilamente o Single Responsibility Principle, porque provavelmente você vai mudar a mesma classe por motivos diferentes. Ou seja, eu posso mudar a minha classe para falar com o banco de dados por um motivo, ou eu posso mudar essa minha classe do Active Record para mexer com comportamento de regra de negócio. Então, claramente, você vê o Active Record quebrando o Single Responsibility Principle. Essa, pelo menos, é a visão que eu tenho. Isso significa que você não deve usar Active Record? Não, não significa isso. Significa que é importante você saber o que ele está quebrando.

Um ponto importante, toda vez que você está usando o ActiveRecord, você vai perceber que, para você desfrutar dos principais recursos que ele traz, você adiciona lógica de domínio nele. E provavelmente você vai ver a sua lógica de domínio vazando para os seus objetos que trabalham com persistência de dados. E é, nesse momento, que a gente começa a ter problemas. Agora, a gente vai ver alguns pontos importantes também. Por quê? Porque apesar de a gente ter esse problema, é um problema, na minha opinião, a lógica de domínio vazar para as suas entidades de banco de dados, ele é muito simples de utilizar. Então, dependendo do projeto, você quer ter uma velocidade, uma facilidade muito grande, você vai perceber que Active Record vai quebrar um “baita galho” para você. Somente para você ter uma ideia. Frameworks que apareceram utilizando o Active Record e foram uma revolução. Se você pegar, por exemplo, a entrada do Rails no mercado, que foi em torno de 2006, você vai ver que uma das grandes facilidades, além de todas aquelas técnicas de scaffolding que o Rails trazia, é a forma de você trabalhar com dados utilizando o Active Record. Tem muita gente que não gosta disso até hoje porque você tem essa mistura de lógica de domínio. Por outro lado, sua velocidade é muito grande. Outro framework que muita gente não gosta por conta de Active Record é o Laravel no PHP. Você vai perceber que você tem uma biblioteca  chamada de Eloquent. O Eloquent é uma forma de você trabalhar com Active Record do Laravel e invariavelmente você vai pegar sua entidade, vai estender do Eloquent e, então, você vai ter todos esses tipos de comportamento e essas possibilidades. Mas novamente você tem esse vazamento de lógica de domínio. Dependendo do projeto está tudo bem ter isso. Tem gente que nem se incomoda, tem gente que se incomoda muito. Então depende muito do nível de purismo que você quer ter  na sua aplicação. Outro camarada que usa Active Record, extremamente famoso, Django. Framework para Python mais famoso que existe. O Django você vai ver que as suas entidades também estendem do Active Record para você conseguir trabalhar. Então, assim, se você pensar bem, você tem três frameworks extremamente sofisticados. Extremamente cheios de recursos que trabalham com esse tipo de padrão.

O ponto importante é que existe como você conseguir ainda utilizar Active Record, mas não ter vazamento da sua lógica de negócios  dentro. Que é você fazer o quê? Comparar o ActiveRecord e toda a sua lógica pensando apenas na camada de dados e você ter uma modelagem de domínio totalmente a parte do seu banco de dados e quando você precisar falar com o ActiveRecord você tem uma camada de abstração. Dá para você trabalhar nesse formato, mas talvez se você quiser trabalhar assim, talvez valha a pena você utilizar outro padrão que não seja Active Record que a gente vai falar daqui a pouco. Minha recomendação pessoal com Active Record, e é pessoal mesmo, seguinte, separe o modelo de domínio do modelo do Active Record. Uma coisa é a entidade pessoa do seu domínio, outra coisa é a entidade pessoa do Active Record. Se você fizer essa separação, você evita esse vazamento. Outro ponto importante, enquanto o Data Table ou o Row Table apenas é acoplado no banco, o Active Record tende também a ficar acoplado no domínio. Eu já falei isso, então tenha ciência disso, saiba quando você vai utilizar um recurso e esse tipo de recurso pode interferir no seu domínio. Agora isso não significa que você não deve usar. Você consegue fazer diversas modelagens, belongs to, has many e tudo mais e está tudo certo. Então, eu não acho que é errado utilizar Active Record, eu já utilizei em diversos projetos, todos rodaram muito bem, muitos já rodam até hoje, mas o maior ponto é você ter essa ciência.
