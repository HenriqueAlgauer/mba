Algumas coisas que eu quero falar, para não gerar confusão com o repositório, porque você deve estar pensando: "Wesley, qual a diferença de Gateway com o Repository? Qual a diferença de data Mapper com o Repository? Qual é a diferença de Repository com Active Record? O meu Repository pode trabalhar com Identity Map e eu posso utilizar Unit Of Work no meu Repository. Então, parece que a gente começa a misturar todos os conceitos que a gente já viu e é por conta disso que o Repository é um padrão muito utilizado, mas a gente vai entender em qual momento está. Então vamos lá: Repository.

O Repository é uma mediação entre a camada de domínio e a camada de dados usando uma interface para acessar os objetos de domínio. O que isso significa? Significa que todas as vezes que você quer fazer com que o seu domínio pegue dados, você vai ter uma interface e essa interface é a interface que a sua abstração de dados vai implementar para você receber os seus dados de domínio. "Wesley, mas qual a diferença disso com data mapper?". Vamos lá! o data mapper apenas faz o mapeamento entre uma entidade de mapeamento com um banco de dados e isso é totalmente independente do domínio da sua aplicação, da lógica da sua aplicação. O Repository é diferente, porque eu vou ter lá os meus objetos de domínio, minhas entidades de domínio, os meus agregados value objects. O que eu vou fazer? Ali na camada de domínio eu vou criar o que no final das contas? Uma interface e eu vou falar o seguinte: "olha quando eu quiser pegar todos os registros eu dou um find all. Quando eu quero pegar somente um registro eu dou um find by id. Quando eu quiser inserir eu vou dar um insert." Então, perceba que a sua camada de domínio, que está definindo como os dados vão chegar para ele. Perceba, o Data Mapper apenas mapeia a entidade com banco de dados e traz retorno. O Repository cria uma interface de domínio, por isso que a gente fala que Repository é um serviço de domínio e não um serviço de aplicação. Existem pessoas que para facilitar o acesso colocam essa interface dentro da pastinha de application. Eu acho que o Brandas normalmente faz isso. Eu não faço isso, eu coloco dentro da pasta de domínio mesmo, porque eu acredito que fisicamente ela faz mais sentido porque ele é um serviço de domínio e não um serviço de aplicação porque quem está determinando como os dados vão ser recebidos vai ser o domínio e não a sua aplicação. Caso contrário você teria apenas um Data Mapper.

Então essa é a ideia do Repository. Como funciona isso na prática? Que media os objetos de domínio e o Data Mapper…então, olha só que interessante. Vamos imaginar que eu criei uma interface chamada find all lá no meu domínio. O que eu faço? Eu crio uma entidade chamada cliente data mapper e faço um mapeamento. Então, no meu objeto, no meu repositório de domínio que eu estou implementando… o que eu vou fazer? Eu posso chamar um Data Mapper e fazer a consulta nos dados. O que eu vou ter que fazer? Eu vou ter que hidratar esses dados com os meus objetos de domínio e retornar isso para o meu domínio. "Wesley está um pouco confuso!" Se você olhar na aula do brandas, ele faz isso claramente ou seja você tem a única diferença é que você pode, por exemplo, no Repository ter um objeto que é em memória, ou você pode fazer um SQL puro, ou você pode utilizar um RM botando um Data Mapper. Então, no Repository, não necessariamente você tem que usar Data Mapper. Dependendo da situação você pode até ter um Active Record para rodar na sua camada de domínio e retornar os dados de objeto.

O Repository não faz distinção de como o objeto é recebido, o que ele faz a distinção é: ele seta uma interface de como os objetos de domínio vão ter que ser entregue, como os dados vão ser implementados para serem buscados no banco não interessa e, nesse caso, eu posso usar SQL puro, posso utilizar RM, posso trabalhar com Data Mapper posso trabalhar com Active Record,  Table Data Gateway… não interessa como, você pode utilizar da forma que você quiser.

Outro ponto que já falei, o repositor recebe os objetos de domínio atendendo uma especificação. Essa especificação é exatamente a nossa interface. Ele retorna os objetos de domínio, então, isso é um ponto importante e é uma característica do Repository. O Repository sempre vai retornar o objeto do domínio. Ele sempre vai retornar sua entidade, o seu objeto de valor, o seu agregado inteiro. Principalmente se você trabalha com o Domain Driven Design é muito comum você encontrar softwares que…o que eles têm no final do dia? Ele cria lá uma pasta Repository. Ele implementa a busca no banco de dados, não interessa como, e na hora de retornar, ele retorna um array ou seja isso não é um Repository. Por quê? Porque esse array não é um objeto de domínio, você tem que retornar o seu objeto de domínio mesmo, a sua entidade que está na lógica de domínio para o Repository. Você pode fazer combinações, o importante é você seguir a especificação da interface e no final do dia você pode trabalhar com SQL etc. Uma coisa bem interessante, também, é que é muito comum você ver o Repository utilizado junto com um padrão chamado de Specification, porque o que o Specification faz? O Specification cria critérios para trazer os dados, então, ele pode colocar um critério assim: "olha, traga para mim como um critério onde o id é igual a 1." Então, isso é um critério de busca e eu posso injetar esse critério no meu Repository e, desse modo, eu consigo fazer as minhas consultas com muito mais flexibilidade ou eu vou criar um critério onde o valor pode ser maior que 100 ou o valor pode ser menor que 50. Ou seja, eu crio critérios, passo esses critérios, essas especificações para o meu domínio, não para o meu Repository. O meu Repository vai trazer esses dados para a gente, ou seja, é muito comum você ver a implementação de Repository recebendo implementações de especificações para você conseguir trabalhar- depois dá uma olhada no padrão Specification, que tem bastante exemplo para vocês.  Então, olha só que interessante, galera. Só para não ficar algo tão aberto, porque essa parte do Repository é o que normalmente a gente utiliza no dia a dia. Eu só quero revisar não sei se você trabalha dessa forma ou não, mas fica ligado no conceito importante. A primeira coisa é que você tem uma Specification, então, perceba que ele coloca como interface. Ele coloca o que eu digo. Eu coloco isso aqui…é um programa, por exemplo, em typescript. Então, eu tenho uma interface de Specification que tem um atributo genérico de um tipo legal e existe um método que eu coloquei isSatisfiedBy o item tal desse objeto  e ele pode retornar true ou false. E o que acontece no meio de toda essa história? A gente pode ter uma especificação concreta, que a gente vai criar, por exemplo, user isMailEmailSpecification implements. Specification de user e de user eu tenho um construtor, onde eu passo um e-mail e eu vou ter ali dentro um método falando isSatisfiedBy, onde vai receber um usuário. Ele vai retornar que usuário que eu passei bate com o e-mail que eu passei no construtor. Se o e-mail que eu passei no construtor bater com o e-mail do usuário que eu passei, esse critério é válido. Isso é um ponto importante. Eu tenho a minha Specification. Você pode ter diversos tipos de Specification.  Você pode ter specification de AND, de OR, de SHOR, de E.  Então você pode ter diversas specifications que você queira implementar e, finalmente, a gente vai fazer uma busca dos dados. Agora quem define o formato dessa busca é a minha interface, é a minha especificação do Repository, que o meu uso é… que a minha entidade usuário está dando. Essa interface é uma interface que fica na minha camada de domínio, ela não fica na minha camada de banco de dados, porque quem está definindo essa interface é o meu serviço de domínio. Isso é um ponto importante. Partindo desse princípio, quando eu coloco interface user repository significa que, quando eu for implementar o meu repositório concreto, eu vou ter que seguir o que… eu vou ter que passar um método, ter um método find by specification, onde eu passo a minha specification de user e eu vou retornar. Perceba, galera, um array de user, perceba que eu não estou retornando um array qualquer. Eu tenho que retornar user porque o meu repositório retorna para mim objetos de domínio. Isso é o ponto mais importante. Então, essa é a minha interface e, por último, eu tenho a minha implementação concreta do meu user repository. Se você perceber, o meu user repository implementa, quer dizer, o meu SQL user repository implementa o user repository, que é uma interface que a gente tem um método find by specification. O que acontece? Esse comentário other implementation details basicamente é onde a gente busca com a SQL select asterisco. Eu vou trazer esses dados de alguma forma, ou eu posso criar outros métodos. Não interessa! O grande ponto é que no meu método find by specification, eu vou passar minha especificação e ele vai fazer uma busca no array de users. A gente poderia está pegando os dados do banco de dados, não interessa, e ele vai ver se o usuário que está passando esse array atende aquela especificação. E qual é a especificação nesse caso? A que o e-mail do cara tem que bater com o e-mail do objeto. Se bater, ele está dando um push, ou seja, adicionando o usuário no array e depois retornando esse array de usuário  no final. Então, se você perceber que o Repository pode… você não necessariamente, galera, tem que utilizar uma specification para utilizar o repositório. Você pode implementar find by id find by name. Você pode dar um delete. Você pode criar find by usuário maior que 10. Você pode criar do jeito que quiser. O grande ponto é que, quando você cria especification, você tem mais flexibilidade. Eu tenho a interface do meu Repository, eu tenho minha specification completa e eu tenho a interface da minha specification.  No final do dia eu vou ter esse tipo de resultado e a minha camada de domínio não sabe como é a implementação do meu repositório, mas ela sabe quais são os métodos que os dados vão ser recuperados. Por isso que a gente diz que repositório é um serviço de domínio, não serviço de aplicação.
