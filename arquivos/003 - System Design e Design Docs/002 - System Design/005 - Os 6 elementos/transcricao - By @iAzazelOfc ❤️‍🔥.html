Bom, pessoal, espero que eu tenha conseguido comunicar e falar da importância que o System Design trouxe para a gente. Mas o grande ponto que a gente vai falar aqui é: basta fazer desenho para gente ter o System Design? Obviamente, eu já falei isso no passado, mas como eu mesmo disse, vamos tentar justificar isso?Não! “Como assim não, Wesley?” Olha só que interessante. Quando você vai trabalhar com o System Design, você vai ter algumas técnicas e algumas metodologias que vão te ajudar a chegar nas soluções.

Eu gosto, normalmente, de falar sobre seis elementos que são importantíssimos na hora vamos pensar em System Design. A primeira coisa que você vai ter que fazer na hora de começar com o System Design: requisitos. Às vezes você está num processo seletivo, às vezes seu chefe pede um negócio para você. Você já sai fazendo, mas você nem fez as perguntas corretas para realmente entender o porquê aquilo está sendo criado. A maioria dos desenvolvedores hoje em dia, que são “escrevedores”, vou até falar assim, os caras que só programam. O que eles fazem? Recebem a ordem e executam. Eles não tentam entender os requisitos e o porquê as coisas estão funcionando daquela forma. Então, a primeira coisa que você vai ter que entender realmente é essa parte de requisitos.

Depois disso, você tem que fazer um plano de capacidade. Ou seja, para ter uma estimativa de capacidade. Como assim? Quantos requests eu vou ter? Quantas compras eu vou ter? Quantas visitas por dia eu vou ter? Eu vou ter pico de acessos? Qual vai ser a minha média de requisição? Quanto eu vou ter que gastar em disco? Quantos requests por segundo? Qual é o meu throughput? Então, esses tipos de coisas são extremamente importantes para, inclusive, eu definir infraestrutura e definir a estratégia, desde tecnologias, linguagens de programação que eu vou utilizar.

Outra coisa, modelagem de dados. E quando eu falo modelagem de dados, eu não estou falando para você criar a estrutura inteira de um banco de dados, mas você, pelo menos, conseguir especificar quais são as principais relações que você tem na hora que você está trabalhando com determinados dados. Inclusive, qual é o tipo de banco de dados que você vai utilizar. Hoje em dia, a gente tem banco de dados relacional, banco de dados chave-valor, banco de dados focados em grafo, banco de dados focado em documentos. Então, qual é o tipo de banco de dados que, talvez, naquela situação, funcione melhor. Assim, modelar os dados, pelo menos nos pontos que mais fazem sentido, é totalmente importante.

E da mesma forma que a gente modela dados, a gente modela a API. E eu não estou falando que você vai ter que programar a modelagem da API. Mas não. Por exemplo, você sabe que uma pessoa vai ter que comprar um ingresso. Então, você vai ter que ter os dados do cliente, qual o ingresso que ele vai comprar e a quantidade. Por que a quantidade? Porque ele pode comprar mais ingressos de uma vez. Então, eu posso ter lá na API um método chamado de comprar ingressos. Entende o que eu estou dizendo? Tem algumas coisas que são muito claras. E o porquê essa modelagem de API é importante? É que as pessoas… para que os stakeholders consigam entender quais são as principais ações que o sistema faz. Quais são as principais chamadas que fazem sentido para você especificar. Obviamente, um sistema pode ter milhões e milhões de linhas, centenas de métodos e endpoints de APIs. Mas você vai perceber que sempre tem aquelas funcionalidades principais. E são essas funcionalidades que você quer enfatizar na hora que você modela uma API.

E um outro ponto… esse sim a gente vai no System Design. (E eu até coloquei aqui em negrito para você, para dizer que nesse momento é a hora do desenho mesmo). É a hora de você desenhar, colocar os elementos, os recursos, a parte de cloud, a parte dos seus sistemas e tudo mais. Essa é a hora do desenho. Pensa o seguinte, os processos de System Design incluem diversos elementos. Dentro dos elementos tem o ato de desenhar. É isso que eu estou querendo dizer agora para você. E, depois disso, a gente tem a parte de exploração. O que é a exploração? Uma vez que eu desenhei, durante o meu desenho ou depois do meu desenho, eu vou tentar ficar me confrontando. Ou alguém vai estar te confrontando. Pode ser tanto na empresa quanto em uma entrevista. Por que você escolheu o Kafka? Por que você está usando o Redis? Por que você não está usando o Memocash em vez do Redis? Esse tipo de coisa é importantíssimo. Então, esse momento de exploração é aquela hora que você simplesmente vai ver se o que você criou, você consegue justificar. É só você pensar, hoje em dia, a gente faz tanta coisa, mas tanta coisa no piloto automático que eu não tenho dúvidas que se eu chegar agora para você e perguntar diversas coisas sobre o sistema que você está criando, eventualmente 10% daquilo que você criou talvez você não consiga justificar. Porque você fez, seguiu convenção, porque alguém utilizou aquela arquitetura e todo mundo está usando aquela arquitetura na empresa por anos e você seguiu a linha. E não tem nada de errado com isso. Agora, já que a gente está estudando isso, vamos tentar justificar aquilo e o System Design vai ajudar você a pensar nesse tipo de coisa. Então, vamos nessa!
