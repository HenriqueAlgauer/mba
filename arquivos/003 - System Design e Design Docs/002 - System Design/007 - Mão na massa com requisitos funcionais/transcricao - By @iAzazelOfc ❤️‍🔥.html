Bom, pessoal, então, agora chegou a hora de a gente colocar a “mão na massa”.  Um dos pontos mais importantes vai ser o seguinte: nós vamos seguir cada uma daquelas etapas para que a gente tenha o nosso System Design pronto, e para isso a gente vai entender as principais técnicas e tudo mais.

Pessoal, o ponto número 1 aqui é em relação a requisitos do sistema. Então, o que eu vou fazer? Eu vou colocar aqui. Uma opção para eu digitar aqui: “ ó, requisitos do sistema”. (Vou colocar aqui para mim em letra bem grandona, vou colocar aqui em vermelho para que a gente consiga saber). Pergunta, se você não sabe qual ferramenta é essa, ela se chama Excalidraw. Eu gosto demais dessa ferramenta porque ela é bem limpa, ela é bem clean. Você consegue entender, fazer seus desenhos e ao mesmo tempo deixar as coisas bem tranquilas.

Bom, a primeira coisa é o seguinte: o nosso sistema vai ser um sistema de ingressos, venda de ingressos online. Um sistema extremamente crítico porque eventualmente quando nós temos shows, temos eventos, esse sistema tem que conseguir suportar uma grande demanda para a gente. Inclusive, tem até picos de acesso, então, a gente começa a pensar um pouco diferente para esse sistema. Mas o negócio é o seguinte, lembra que eu falei que a gente estava pensando em requisitos? Vamos colocar o seguinte, requisitos funcionais. O que são requisitos funcionais? As principais funcionalidades, nesse caso, do nosso sistema. E eu quero dividir essas funcionalidades aqui para vocês. Com as funcionalidades Core do nosso sistema… vou até colocar aqui em azulzinho para ficar mais claro aqui para gente, para que nós possamos entender quais são as tais funcionalidades. Então, quais vão ser essas funcionalidades? Bom, deixa eu colocar aqui em preto e com uma fonte um pouco menor aqui para que a gente consiga entender quais são essas funcionalidades. Primeira funcionalidade, o que um sistema de ingresso faz? Compra de ingressos, o usuário vai poder fazer o quê? Comprar ingressos aqui para a gente. Esse aqui é o principal ponto que nós temos que levar em conta. Eu vou deixar esse aqui como large. A gente vai ajustando esses pontos aqui.

Então primeira coisa, compras de ingressos. A segunda coisa que a gente vai ter, é apresentar o ingresso comprado para entrar no evento. Logo, isso é uma coisa que normalmente é bem crítica. Você compra o ingresso e você tem que conseguir exibir esse ingresso na hora da entrada. E uma coisa que também é super importante para esse tipo de sistema é que a gente tem parceiros para gerenciar os eventos. Olha só que interessante! Pode parecer algo muito bobo ou até mesmo muito simples, mas se você pensar bem, essa aqui é a nossa funcionalidade Core. Como eu sei disso? Eu estou dando esse cenário, mas vamos imaginar que você está numa entrevista, você está numa situação… você vai chegar e vai falar para a pessoa: “meu, o que faz seu sistema de ingresso, que você quer criar?” Ah, o cliente vai lá, compra o ingresso, e depois que ele compra o ingresso, na hora de entrar no show ele mostra o ingresso. “Poxa, mas quem que vai administrar tudo isso?” Ah, o que vai acontecer é porque a gente tem vários parceiros e os parceiros cadastram os eventos.

Então, vamos imaginar jogos de basquete. Eu vou pegar, por exemplo, a liga de basquete e eles vão cadastrar os eventos para vender os tickets de basquete. Então, os parceiros precisam gerenciar. Entendi a ideia do sistema. Agora quais outras funcionalidades a gente tem para que essas funcionalidades aqui de cima façam sentido? Então, eu vou chamar isso aqui de funcionalidades de suporte. Essas funcionalidades de suporte vão fazer com que essas funcionalidades daqui de cima façam sentido. Quais vão ser as nossas funcionalidades de suporte aqui nesse nosso caso? Eu vou colocar o seguinte: (Lembrando, pessoal, isso aqui é um exercício para que você consiga entender um ciclo completo de um System Design) a primeira coisa é que o cara vai comprar o ingresso, vai. Então, ele vai ter que fazer o pagamento. Logo, ele vai fazer assim: “ó, o pagamento e o split do pagamento.” Por que o split? Porque uma parte vai para o parceiro e outra parte vai para a plataforma de ingressos. O que ele vai ter que fazer também para conseguir comprar os ingressos? Ele vai ter que poder fazer uma busca dos eventos que estão anunciados. O que mais a gente tem que ter? A exibição gráfica dos lugares disponíveis. Isso é uma coisa bem importante. Eu vejo todas as vezes porque eu vou muito em jogo de basquete, etc. você vai lá e vê onde vai ser a sua posição ali na hora de você conseguir fazer a compra do seu ingresso.

Outra coisa importante aqui é a garantia que em horários de pico. Assim, eu vou colocar aqui que, em horários de pico, um ingresso não seja vendido para mais de uma pessoa. Por que eu estou colocando isso aqui? Porque, isso aqui é extremamente crítico. É um problema clássico de concorrência. Quando vocês têm muitos acessos simultâneos e você não conseguir pensar em concorrência nesse momento, definitivamente você vai vender mais de um ingresso para, quero dizer, o mesmo ingresso para mais de uma pessoa. Então, isso aqui é extremamente crítico para você pensar com a gente. Obviamente, eu poderia passar horas e mais horas colocando as funcionalidades do sistema. Mas eu estou colocando aqui uma ideia de um domínio que eu acho que é fácil de todo mundo entender.

Então, eu preciso comprar o ingresso, preciso mostrar ingresso e eu preciso gerenciar os eventos. Eu preciso, para comprar… eu preciso ter o pagamento, split de pagamento, para eu acessar um evento. Eu tenho que buscar para que, na hora de comprar, eu tenha que ver o local gráfico de onde vai estar. Além disso, eu também, na hora do pico, tenho que garantir que eu não vou vender para mais de uma pessoa. Então, essas funcionalidades de suporte aqui vão realmente me ajudar. Logo, isso aqui é um ponto importante. Todas as vezes que você for pensar num sistema de design, você tem que pelo menos ter algo assim esquematizado. E, com isso, você pode destrinchar, ir mais a fundo, pegar muitas funcionalidades, e você pode fazer uma modelagem eventualmente de domínio para saber o que, nesse sistema, nessa solução, vale a pena ter, vale a pena não ter. Mas o nosso principal ponto aqui é que você consiga entender que essa é a nossa primeira etapa. No próximo vídeo, a gente vai seguir a etapa para falar de requisitos não funcionais. Então, vamos nessa!
