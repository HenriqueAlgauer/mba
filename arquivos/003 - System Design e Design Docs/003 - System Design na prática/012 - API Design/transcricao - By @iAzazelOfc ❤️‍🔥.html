Bom, pessoal, agora a gente vai para uma outra área aqui, que ainda contempla a parte de System Design, é a parte da API Design, ou seja, o design da sua API. Como assim? Novamente, a nossa ideia aqui não é criar a API aqui, mas novamente é que, quem olhar esse documento, vai conseguir perceber como as operações vão funcionar. E aqui, nesse nosso caso, a gente precisa apenas mostrar a principal operação ou as principais operações.

Então, nesse nosso caso aqui, API Design. Quais são as operações que são mais importantes para mim? Se você pensar bem (deixa eu trazer esse cara aqui para mim) a minha principal operação é comprar ingresso. Como eu compro o ingresso aqui para mim, no final das contas? Eu vou ter que fazer uma ordem de serviço. O que eu posso chegar aqui? Eu posso chegar aqui e falar: “olha… (deixa eu até usar uma fonte retona normal) eu vou criar um Place Order aqui para mim, onde eu vou ter um User ID, eu vou ter um Event ID e um Spot ID”. Eu tendo isso aqui é a forma que já fica mais fácil de eu conseguir compreender como vai funcionar o processo da compra. (Eu não estou gostando dessa fonte ainda, assim ficou melhor, ficou com mais cara de código). E não é Spot ID, Spot ID, ou seja, o local onde esse ingresso vai colocar. Então, quando eu tenho essa informação, eu consigo fazer o meu processo de compra. Qual vai ser a minha response por conta disso aqui? E tente detalhar de forma geral, ao máximo, como vai funcionar a sua response, o que você vai retornar de informação para esse cara aqui. E aqui na minha response eu vou retornar simplesmente o Order ID e o Ticket ID, no final do dia é isso que eu vou querer ter comigo, assim que eu fizesse a minha compra, porque o Order ID quer dizer que ele já gerou uma nova order e essa nova order foi aprovada e o Ticket ID foi aqui para mim também gerado. Eu tendo essa informação, eu sei que eu consigo trabalhar. Então, se você olhar, esse tipo de coisa acaba sendo bem simples, bem tranquilo aqui se você perceber. Aqui, caso você queira, você pode até colocar o código HTTP, sei lá, 201 created. Você consegue mostrar para o usuário final como vai ser esse processo internamente, não necessariamente no código, mas como a API vai trabalhar na hora de se comportar dentro do seu sistema. Da mesma forma aqui eu vou ter o visualizar ingresso, visualizar. Como vai funcionar a visualização do nosso ingresso? Eu posso pegar aqui um GetTicket, ou ViewTicket, e aqui eu vou ter o meu Ticket ID, e eu tendo o meu Ticket ID, o que eu vou precisar aqui para mim? O Order ID, o User ID, o User Name, o Event Name, o Event Date, o Spot e o total que foi pago aqui para isso, porque isso aqui é o que vai aparecer no final do dia no bilhete do cara.

Então, com isso aqui, eu sei quem está fazendo a compra só de olhar isso aqui. Pessoal, perceba, é algo muito “bobo”, parece muito “bobo”, mas quando você olha você fala: faz sentido. Para comprar eu tenho um Place Order. Eu vou ter no final do dia o Order ID e o Ticket ID aqui comigo, que foram gerados, e ao mesmo tempo quando eu quiser ver um Ticket, são essas informações que eu vou precisar, porque essas são as minhas operações Core. Lembra, quando a gente está fazendo System Design, você vai pegar suas operações Core, as outras operações você vai deixar de lado porque são operações de suporte, a não ser que elas façam muito sentido, sejam muito importantes de forma geral de aparecerem, mas você não vai querer documentar API, modelagem de tudo, do seu sistema inteiro, porque nesse momento você não está com o papel de desenvolvedor. Você está com o papel de arquiteto de solução. Obviamente, quanto maior o risco do projeto mais você documenta. Quanto maior o risco do projeto, o que você vai fazer? Você sim, vai poder documentar, criar desenhos de outras partes do sistema, não tem problema nenhum.
