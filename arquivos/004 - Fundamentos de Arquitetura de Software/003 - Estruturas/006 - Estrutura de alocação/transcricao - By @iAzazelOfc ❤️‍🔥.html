Bom, pessoal, agora a gente vai falar sobre estrutura de alocação. Pode parecer um nome um pouco estranho, mas você vai entender que faz sentido. Até agora a gente olhou como os componentes se conectam através de conectores. A gente conseguiu olhar como os módulos se falam, as suas dependências e o que você faz para diminuir o acoplamento, mas tanto a estrutura de componentes e conectores quanto a estrutura de módulos precisam estar…. executar em algum lugar.

Então, a estrutura de alocação é a relação das estruturas, componente, conector e módulos, e como elas se conectam com não-software. O que significa? Quando eu vou criar uma estrutura de alocação, eu tenho que pensar: “meu, para rodar isso aqui eu preciso… qual tipo de máquina, qual tipo de computação?” Eu vou precisar ter uma máquina que vai gravar para caramba. Eu vou ter uma máquina que vai precisar ter muita memória. Eu vou ter que entender o tipo de computação. Eu vou ter que ter os ambientes. Como eu vou fazer com os ambientes que eu vou trabalhar, para eu conseguir trabalhar, desde o ambiente de teste? Como esse processo vai funcionar? Então se você perceber, a estrutura de alocação dá suporte para a estrutura de software que você está criando. Porque sem ela, você não tem onde realizar as ações que você está querendo. Assim, como eu vou testar? Eu tenho os testes automatizados? Tenho, mas eu vou ter equipes de QA, por exemplo? Como isso vai ser executado? Onde os testes vão ser executados e qual o momento? Como vai funcionar? Como você vai realizar o build dessa aplicação para você entregar? Como você vai fazer o deployment dessa aplicação? Qual tipo de disk? Qual tipo de banco de dados? Quais são os tipos de cache? Como você consegue evitar lock-in? Como você vai utilizar o seu cloud provider? Quais os cloud providers, prós, contras? Como eu vou pensar no que gasta mais, no que não gasta mais, ou seja, no que é viável para o meu projeto? Então, olha só que interessante, galera. Quando você vê que as coisas se conectam, quando você dá um zoom, entende esses módulos. Você vai ter que entender como essas coisas vão se encaixar para rodar em algum lugar. E esse rodar em algum lugar significa, no final do dia, como essas coisas vão ser, no final do dia, deployadas. Como o deployment vai acontecer? Como as coisas vão funcionar em produção? Como os meus ambientes vão ser criados para facilitar o meu dia a dia?

Portanto, quando você consegue olhar a sua arquitetura nessas visões, você consegue ter uma visão muito mais clara do que você começar um projeto e falar: “por onde eu começo?” Reflete  comigo nesse momento. Se der um desafio para você, você vai pensar por onde você vai começar? Perceba. Você tem que ter um método. E esse método de por onde começar, significa que você vai ter que ter pontos de visão diferentes para que você comece a estruturar o seu software de forma diferente. E fazer isso que estamos falando aqui é o que vai ajudar minimamente você a ter um método de olhar para o seu software. E lembrando, nesse caso aqui, a gente tem muito a aprender com código, mas indiretamente você olha um pouco, tem um pouco de arquitetura de solução. É aquela história, galera, design e arquitetura de software, arquitetura de solução e arquitetura de software. Sempre há uma zona cinzenta. O arquiteto de software tem que saber navegar entre essas zonas cinzentas. Ele tem que entender como o software vai rodar e aonde vai rodar, e qual a performance que esse software vai ter. Então, de uma forma ou de outra, a estrutura de alocação é um ponto importante. É isso!
